# AGENTS.md — ALPOOL Admin

## 1. Назначение проекта

ALPOOL Admin — внутренняя веб-панель управления для компании ALPOOL.

Основной production API:

https://api.alpool.ru

Админка является только frontend-приложением.
Она не должна дублировать backend-логику, создавать собственную базу данных или реализовывать отдельную серверную систему.

Backend находится в отдельном проекте `alpool-backend`.

Основной публичный сайт ALPOOL также является отдельным проектом.

---

## 2. Основной стек

Использовать:

- React
- TypeScript
- Vite
- React Router

Дополнительные зависимости добавлять только при реальной необходимости.

Не использовать без отдельного согласования:

- Next.js
- собственный Node.js backend
- SSR
- собственную базу данных
- тяжёлые UI-фреймворки
- сложные state-management библиотеки
- Docker
- микросервисную архитектуру

Предпочитать стандартные возможности React, TypeScript и браузера.

---

## 3. Архитектура

Предпочтительная структура:

src/
  api/
  auth/
  components/
  layouts/
  pages/
  types/
  utils/

public/
tests/

Назначение:

- `api/` — HTTP-клиент и функции взаимодействия с ALPOOL API.
- `auth/` — авторизация, JWT, состояние сессии и защита маршрутов.
- `components/` — переиспользуемые UI-компоненты.
- `layouts/` — общий интерфейс административной панели.
- `pages/` — страницы приложения.
- `types/` — TypeScript-типы API.
- `utils/` — небольшие общие вспомогательные функции.

Не создавать лишние уровни абстракции без необходимости.

---

## 4. API

Production API:

https://api.alpool.ru

Не хардкодить API URL по всему приложению.

Использовать единую конфигурацию, например:

VITE_API_BASE_URL

Создать `.env.example`, но никогда не добавлять реальные секреты в Git.

Адрес production API не является секретом.

Все запросы к backend должны проходить через единый API-слой.

Не дублировать fetch-логику по компонентам.

---

## 5. Авторизация и безопасность

Backend использует JWT.

Frontend должен:

- иметь отдельную страницу входа;
- отправлять логин и пароль только backend API;
- никогда не хранить пароль администратора;
- не выводить JWT в интерфейс или console.log;
- добавлять JWT в `Authorization: Bearer <token>` для защищённых запросов;
- корректно обрабатывать 401;
- позволять пользователю выйти из системы;
- после выхода удалять клиентскую сессию.

Не добавлять:

- пароли;
- JWT;
- SSH-ключи;
- GitHub tokens;
- API secrets;
- другие секреты

в исходный код, Git, README, тестовые fixtures или `.env.example`.

Безопасность административной системы должна обеспечиваться backend, а не сокрытием frontend-кода.

Не считать клиентскую проверку маршрутов механизмом безопасности API.

## 6. Первая версия — v1

На первом этапе реализовать только:

### Login

Маршрут:

/login

Функции:

- логин;
- пароль;
- вход;
- отображение понятной ошибки авторизации.

### Leads

Маршрут:

/leads

Функции:

- получение списка заявок;
- отображение основных данных;
- статус заявки;
- дата создания;
- телефон;
- email при наличии;
- источник;
- переход в карточку заявки.

### Lead details

Маршрут:

/leads/:id

Функции:

- полные данные заявки;
- сообщение;
- UTM-параметры при наличии;
- изменение статуса через существующий backend API;
- список вложений;
- скачивание вложений через существующий backend API.

### Logout

Должен полностью завершать клиентскую сессию.

## 8. Интерфейс

Стиль:

сдержанная премиальная инженерная административная панель.

Основные принципы:

- светлая рабочая область;
- тёмная боковая навигация;
- высокая читаемость;
- спокойная типографика;
- минимум декоративных эффектов;
- понятная визуальная иерархия;
- аккуратные таблицы и карточки;
- понятные статусы заявок;
- хороший contrast;
- заметные, но не агрессивные действия.

Админка должна выглядеть как профессиональный рабочий инструмент, а не как рекламный лендинг.

Не копировать дизайн публичного сайта буквально.

---

## 9. Responsive

Интерфейс должен нормально работать:

- на desktop;
- на ноутбуке;
- на планшете;
- на современном смартфоне.

Не делать desktop-only таблицы, которые невозможно использовать на телефоне.

Для мобильного интерфейса допускается переход от таблицы к карточкам.

---

## 10. UX

Обязательно предусматривать:

- loading state;
- empty state;
- error state;
- disabled state во время отправки;
- подтверждение успешного изменения;
- понятную обработку сетевых ошибок;
- обработку истёкшего JWT;
- отсутствие необработанных Promise errors.

Не использовать `alert()` как основной UI-механизм.

---

## 11. TypeScript

Избегать `any`.

Типы ответов backend должны быть явно описаны.

Не придумывать поля API.

Перед реализацией функций, зависящих от backend, проверять существующую OpenAPI-схему или backend-код.

Если backend не предоставляет необходимую возможность — сообщить об этом, а не имитировать её во frontend.

---

## 12. Качество кода

Перед завершением задачи:

1. проверить TypeScript;
2. выполнить production build;
3. запустить существующие тесты;
4. проверить отсутствие случайно добавленных секретов;
5. проверить `git diff`;
6. сообщить обо всех предупреждениях.

Не скрывать ошибки тестов или build.

Не исправлять несвязанные проблемы без необходимости.

---

## 13. Git

Без отдельного разрешения пользователя:

- не выполнять `git push`;
- не делать production deploy;
- не подключаться к VPS;
- не менять DNS;
- не менять Nginx;
- не менять backend;
- не менять основной сайт.

Локальные изменения разрешены в рамках поставленной задачи.

Перед commit показать итог выполненной работы.

---

## 14. Production

Планируемый адрес административной панели:

https://admin.alpool.ru

До отдельного этапа deployment:

- не менять DNS;
- не создавать production-конфигурацию сервера;
- не менять CORS backend самостоятельно.

Для работы `admin.alpool.ru` backend позднее должен явно разрешить этот Origin в CORS.

## 15. Принцип разработки

Перед изменением:

1. изучить существующий код;
2. понять текущую архитектуру;
3. использовать существующие решения проекта;
4. сделать минимально достаточное изменение;
5. покрыть критическую логику проверками;
6. проверить результат.

Не переписывать рабочий код только ради другого стиля.

Если задача неоднозначна или требует изменения архитектуры — сначала сообщить об этом.

ALPOOL Admin должен оставаться простым, предсказуемым и поддерживаемым.
